# Описание проекта

## Назначенное задание

Команда 14, [P23: PagedAttention — управление памятью KV-кэша](https://distsys.ru/osukhoroslov/nis2/src/branch/main/project-tasks/p23-pagedattention.md), версия карточки 1.1 от 07.09.2026. Основной источник — [Kwon et al., SOSP 2023](https://arxiv.org/abs/2309.06180), разделы 3–4: резервирование, блоки и отображение логических позиций в физическую память. Проверяем управление памятью и возможность размещать больше запросов при одинаковом бюджете.

## Выбранный технический путь

**Самостоятельная реализация на CPU**, предусмотренная карточкой. Python 3.9+, стандартная библиотека, один процесс и один поток. Оба аллокатора используют реальный заранее выделенный массив `bytearray`; чтение и запись проходят через таблицу размещения. Арифметический расчёт служит независимым эталоном маленьких примеров. Это не чистая имитация памяти.

Авторский vLLM не является исполняемой зависимостью этого пути. Для сверки терминов и устройства блоков зафиксирована ревизия [`3e9d364ff727f002680d242ea76e8a0bbdc0163c`](https://github.com/vllm-project/vllm/tree/3e9d364ff727f002680d242ea76e8a0bbdc0163c), раскрывающая короткий SHA из карточки. Доступен [пул блоков](https://github.com/vllm-project/vllm/blob/3e9d364ff727f002680d242ea76e8a0bbdc0163c/vllm/v1/core/block_pool.py). Код vLLM в проект не копируется; запуск GPU-ядра не заявляется.

## Поддерживаемые сценарии

1. Две короткие последовательности с завышенным пределом длины: проверяем разницу между полезными байтами и закреплённой ёмкостью.
2. Рост через границу блока: новая страница появляется только при необходимости; при исчерпании пула запрос получает явный отказ без потери старых данных.
3. Освобождение запросов в разном порядке: непрерывные свободные участки могут оказаться несмежными; paging повторно использует отдельные блоки.
4. Планируемый динамический поток: короткие, длинные и смешанные запросы, равномерные и пакетные поступления; один и тот же порядок обработки и бюджет для обоих методов.
5. Отрицательный контроль: при достаточной памяти и близких к пределу фактических длинах преимущество paging может исчезнуть; накладные расходы таблиц могут увеличить задержку.

Текущие трассы не содержат полноценного планировщика: `active_requests` в свидетельствах означает число резидентных последовательностей. Размер динамического пакета будет отдельно измеряться после реализации обработчика.

## Упрощения

- Вместо LLM — детерминированный генератор байтов; KV одного токена — фиксированный payload. В прототипе следующий payload зависит от предыдущего прочитанного. Не считаем attention, качество генерации или стоимость GPU.
- Общий физический пул создаётся заранее. `allocated_bytes` означает закреплённую запросами часть пула; физический размер пула одинаков и не уменьшается при освобождении. Python-объекты и RSS измеряются отдельно в будущем эксперименте.
- First-fit baseline резервирует объявленный верхний предел без перемещения. Это явно выбранный baseline, а не универсальная модель всех непрерывных аллокаторов.
- Основной paging без prefix sharing, copy-on-write, swap и вытеснения. Уменьшение обязательного объёма не требуется: эти механизмы в карточке необязательны.
- Синтетические длины и поступления известны генератору; аллокатор и планировщик не получают фактическую будущую длину до остановки запроса.
- CPU-задержки относятся к учебному обработчику. Результаты не переносятся на полноценный LLM-сервер, GPU-ядра или коэффициенты ускорения из статьи.
